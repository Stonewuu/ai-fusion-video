# Flyway 迁移命名约定

## 文件名

版本化迁移统一使用：

```text
V1.<产品主版本>.<产品次版本>.<产品修订版本>.<迁移序号>__<英文描述>.sql
```

- `V1` 是历史遗留的 Flyway 版本前缀，为兼容已部署数据库永久保留。
- `<产品主版本>.<产品次版本>.<产品修订版本>` 必须与迁移所属的产品版本一致。
- 同一产品版本内的迁移序号从 `0` 开始连续递增。
- 描述使用小写 snake_case。
- 新功能开始前核对正式 Release/Tag；已发布产品版本不再追加迁移。前后端先提高产品版本，再从新版本的序号 `0` 开始。不能仅因工作区仍写着旧版本号，就把新迁移归入已发布版本。

例如，产品版本 `1.0.0` 的前两条迁移为：

```text
V1.1.0.0.0__first_change.sql
V1.1.0.0.1__second_change.sql
```

## 基线迁移

稳定版本可以额外提供一条 Flyway Baseline Migration，用于让全新空数据库跳过此前的
全部 V 迁移。文件名使用：

```text
B1.<产品主版本>.<产品次版本>.<产品修订版本>.<迁移序号>__baseline_<产品版本>.sql
```

开发中的产品版本不保留 B 基线；表结构仍可能变化时继续增加 V 迁移。产品版本稳定后，
再从执行完该版本全部 V 迁移的全新数据库生成基线，且基线版本必须与快照覆盖的最后一条
V 迁移完全一致。

- 基线必须从一个执行完对应全部 V 迁移的全新数据库导出最终结构和必要初始化数据。
- 导出时必须排除 `flyway_schema_history`、数据库名、`CREATE DATABASE` 和 `USE`。
- 全新空数据库会使用最新基线，再执行版本高于基线的 V 迁移。
- 已有 Flyway 历史的数据库会忽略基线，继续执行原有 V 增量迁移。
- 基线不能代替或删除旧 V 迁移；已发布的基线同样是不可变历史，必须永久保留。

## 发布边界与开发版调整

已发布版本及更早版本的 V、B 迁移是不可变历史，不得修改内容、版本或文件名。仓库中的
`V1__init_mysql.sql` 以及 `V1.0.2.0.1` 至 `V1.0.6.1.5` 保留为历史兼容例外。

当前尚未发布的开发版本只在必要时调整已有迁移，例如修复执行失败或纠正结构错误，
不能仅为整理或个人偏好反复修改。修改前核对正式 Release/Tag、已执行环境与影响，记录
必要性、具体差异和验证结果；在临时测试库执行不等于正式发布。

调整已经执行的开发版迁移时，可丢弃的本地或临时测试库优先重建。需要保留数据时先
备份：仅改名须确认 SQL 内容和 checksum 不变，再同步 `flyway_schema_history.version`
与 `script`；修改 SQL 须先同步实际结构、核对一致性，再同步相应 checksum。两种情况
均须完成 Flyway validate 和迁移命名测试。`flyway repair` 不能把旧版本映射为新版本，
也不能替代实际结构同步。共享或生产环境的数据及历史操作仍须具备对应环境的明确授权。

## 1.3.0 发布前合并

1.3.0 的开发迁移在正式发布前从 38 个合并为 7 个。新建表直接包含最终字段、索引和约束；
已有表的相关修改合并到同一条 ALTER，视图只创建最终定义。

| 序号 | 内容 |
| --- | --- |
| 0 | 画布文档、操作历史和固定结果 |
| 1 | 业务版本、命令、变更通知、内容历史和项目成员变更 |
| 2 | 托管媒体、文件、业务引用和清理状态 |
| 3 | 生成任务、媒体任务、预览和 ComfyUI 试运行 |
| 4 | 画布执行、文本与 MCP 调用、媒体导入和交付 |
| 5 | 智能体作用域、用户配置和提供商配置 |
| 6 | 媒体引用与保留检查视图 |

从已发布版本升级时，仍由 Flyway 正常执行迁移，不需要手工修改迁移记录。
已经执行过原来 38 条开发迁移的数据库，则需要先备份并确认最终结构一致，再同步本版本的
迁移历史。不能直接重新执行合并后的建表脚本，也不能只修改 checksum 或运行 repair。
