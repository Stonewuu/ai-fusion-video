# Agent 事件持久化优化方案

状态：历史备选分析，依据为 2026-11-24 优化前的七组实测和当时的代码。

方案范围补充：本文保留为 MySQL 继续保存流式事件时的备选分析。实际已经采用 Redis 保存增量、MySQL 保存完整消息和工具记录的方案，详见 [交付总结](../3-completed/20261124-Redis流式与消息持久化/completion-summary.md)。两种方案的收益数字不能混用。

当前优先范围收窄为消息、工具调用参数与结果、消息计数及相关状态保存。心跳、模型额度和工具修改业务资源的写入不作为这一轮的主要改动对象。框架归属已核对当前依赖 AgentScope 2.0.4 的本地 sources.jar。

建议分三步实施：先精简重复生命周期记录、合并消息和会话更新；再把事件改为小批量提交，并让父运行引用子事件正文；最后优化心跳的提交方式。保留现有 SSE 协议、运行内连续序号、先提交再推送、所有者校验和状态快照。

## 1. 短回复为什么也有 36 次写入

“监测完成。”的完整过程包含 36 条有效写 SQL：9 条事件及其序号更新占 18 条，心跳占 3 条，运行、会话、消息、状态快照和模型请求记录占 15 条。这是语句次数，不是把正文保存了 36 份。

9 条事件中，前端收到的只有 CONTENT 和 RUN_TERMINAL/DONE。其余是 AGENT_START、MODEL_CALL_START、TEXT_BLOCK_START、TEXT_BLOCK_END、MODEL_CALL_END、AGENT_RESULT、AGENT_END。

其中 AGENT_START 暂时保留：画布节点派发及外部等待恢复会检查 `next_sequence` 是否前进。没有启动标记时，已开始的执行可能在首次文本到达前仍被当成尚未启动。未来若改为明确的执行启动字段，需要同时修改相关恢复判断，不能只删除事件。

其余六类在 `outputType == null` 时属于本轮优先精简范围。当前回放从 MySQL 读取已提交记录，最终消息由内容、工具和控制事件整理，运行终态由独立的终态事务决定。模型开始、结束状态另有模型请求和用量记录，因此无需再把这些生命周期标记及完整 AGENT_RESULT 正文重复存入事件表。

**精简发生在持久化入口，不取消 SDK 事件，也不跳过已有中间件和合并器。** TEXT_BLOCK_START 仍要参与思考时长计算，AGENT_END 仍要经过关闭恢复中间件。只有这些处理完成后，才决定是否写事件表。

## 2. 哪些保留，哪些调整

| 写入对象 | 处理建议 | 保留原因或调整边界 |
| --- | --- | --- |
| 用户消息、运行受理、权限与配置快照 | 保留，合并受理事务 | 保证消息和执行身份一致，后续配置变化不能改变已受理任务 |
| AGENT_START 启动标记 | 首期保留并立即提交 | 现有派发和恢复判断依赖事件序号是否前进 |
| CONTENT、REASONING | 保留；合并片段和批量提交 | 已展示内容必须能在断线或重启后回放 |
| TOOL_CALL_DELTA、TOOL_RESULT_*_DELTA | 保留 | 工具参数和结果由这些片段重建，不直接显示不等于可以删除 |
| 工具调用/完成、子任务状态、模型重试、审批、外部等待、取消、终态 | 保留，作为及时提交的边界 | 决定界面状态、后续执行和故障处理 |
| 六类重复生命周期标记，且 outputType 为空 | 停止写主事件表；需要时记诊断日志 | 限于上述明确类型，不能按“未推送”统一删除 |
| next_sequence | 每批更新一次 | 序号与事件必须在同一事务提交，不能先领取一段号码后异步填空 |
| 父运行复制的子事件 | 正文改为引用，保留父序号 | 父时间线需要持久化顺序，正文不需要重复保存 |
| 会话消息计数、下一消息序号、最后消息时间、终态 | 在同一批历史保存中合并更新 | 不需要每插入一条历史消息就更新一次会话 |
| AgentState 状态快照 | 首期保留 | 当前用于暂停、重试、关闭恢复和完成前校验，不能用文本日志替代 |
| 模型请求与用量记录 | 保留 | 请求表承担未知提交和并发状态，用量表承担调用结果；不能仅因字段相似而删掉一张表 |
| 心跳与租约 | 保持检查时效，合并数据库提交 | 还承担丢失取消通知后的状态检测，不能只调大间隔 |
| 业务命令、版本和资源事件 | 保留业务语义 | 用于幂等、资源历史及业务结果，后续单独评估批量写入 |

六类精简名单为 MODEL_CALL_START、MODEL_CALL_END、TEXT_BLOCK_START、TEXT_BLOCK_END、AGENT_RESULT，以及不对外发布的 AGENT_END。SUB_AGENT_FINISHED 对应的 AGENT_END 继续保留。未列出的事件默认沿用已有持久化规则。

### 消息与工具记录由谁保存

| 内容 | 触发方及调用链 | 判断 |
| --- | --- | --- |
| 用户消息 | 项目 AgentRunCoordinator → AgentMessageAllocator → afv_agent_message | 必要；与受理状态及消息计数合并事务 |
| 助手最终回复、工具参数、工具结果的历史消息 | 项目 AgentMessageProjectionService → AgentMessageAllocator | 必要的历史读取数据；当前不随每段文本更新消息表 |
| 消息顺序、数量及最后消息时间 | 项目 AgentMessageAllocator 每插入一条消息就更新 afv_agent_conversation | 可改为每批历史消息更新一次 |
| 流式及工具事件 | 框架产生事件；项目 DefaultRunExecutionSupervisor → MySqlAgentEventRepository 决定逐条写库 | 逐条落库及逐条更新序号不是框架要求，可精简、合批 |
| 子事件复制到父运行 | 项目 DefaultRunExecutionSupervisor.mirrorToParent | 属于项目实现，可改为顺序引用和父子同事务 |
| 模型下一轮需要的工具调用与结果 | 框架先加入 AgentState.contextMutable 的内存列表 | 并非每追加一条内存消息就执行数据库写入 |
| 开始时的状态快照 | 项目 applyRequestedPolicy → SDK setPermissionMode → installPermissionContext → saveAgentState → MysqlAgentStateStore | 项目主动设置权限，框架负责执行持久化；不是框架固定的启动写入 |
| 执行完成、失败、中断或等待时的上下文 | 框架 ReActAgent 的状态保存流程 → 项目包装的 AgentStateStore → MysqlAgentStateStore | 保留，用于下一轮、重试和恢复 |
| 关闭恢复成功后的确认 | 项目 AgentScopeShutdownRecoveryBridge.acknowledge → store.save | 只在对应恢复路径触发，本次普通对话没有这一额外写入 |
| 超长工具结果全文 | 项目 LongToolResultMiddleware → LongToolResultStore → 工作空间存储 | 已按内容版本去重；可继续让事件和历史复用其正文，但需统一权限、保留期和读取方式 |

普通短回复和只读工具测试都只有两次 AgentState 写入：开始时由项目应用权限策略触发一次，结束时由框架保存完整状态一次。完整解析的八次可对应为两个 agent 的两次权限设置、两次完成保存及四次模型失败后的状态保存。模型重试由项目中间件发起，失败后安全上下文的保存由框架执行。

项目已关闭 SDK 的本地 transcript、默认 session 文件持久化、内置 memory hooks 和 tool-result eviction。当前主要的正文副本来自事件日志、项目历史消息、AgentState，以及超长结果的工作空间存储；不能把数据库写入都归因为 SDK 自动保存聊天记录。

历史消息、事件日志和 AgentState 的用途不同：历史消息供界面及历史重建使用，事件支持流式和重连，AgentState 保存模型继续执行所需的结构化上下文。三者包含同一段正文不代表三者都能删除。应优先消除重复正文、重复元数据更新及不参与恢复的生命周期记录。

### 消息范围内的优化优先级

1. 优先合并会话计数和历史消息写入。只读工具样本的四条历史记录分别是用户消息、工具调用参数、工具结果和助手回复，语义合理；六次会话 UPDATE 则有合并空间。
2. 保留工具调用与结果的关联，不优先把两条记录改成一条可变记录。若只是将两次 INSERT 换成 INSERT 加 UPDATE，写 SQL 次数没有减少，却需要改变历史读取和幂等键。
3. 精简重复生命周期事件，合批写事件和序号，并让父事件引用子正文。完整工具参数和结果仍需可重建，不能先删片段再留下只含调用 ID 的结束事件。
4. 对超长工具结果，沿用已有分段读取协议，让事件、父引用和历史详情复用一份持久化正文。模型上下文继续遵循现有长结果处理方式，不能直接把无法解析的引用送给模型；引用的有效期至少覆盖历史消息的有效期。
5. 优化重复权限设置。applyRequestedPolicy 目前每次调用 setPermissionMode，即使规则没有变化也会保存整份状态。后续会话可以在确认本用户、本会话的完整持久化权限规则未变时跳过重复设置；首次会话、规则变化和恢复路径继续保存。必须比较完整规则和工具集合，不能只比较模式枚举，也不能依赖共享 agent 的陈旧内存状态。

权限设置优化不计入第 8 节的新会话收益数字，因为新会话仍保留首次保存。它主要减少同一会话后续轮次中未变权限引发的整份状态重写。框架在完成、失败及暂停时保存的状态暂不精简。

## 3. 小批量提交事件

当前一条事件对应一个事务，其中执行一次运行序号 UPDATE 和一次事件 INSERT。改为一个批次中的 N 条逻辑事件仍占 N 个连续序号，但只更新一次运行序号，再执行一条多行 INSERT。

普通事件批次的顺序为：

1. 在事务外收集和序列化事件，限制排队条数及字节数。
2. 开启短事务，锁定运行行，校验所有者、执行代次 ownerEpoch、租约、运行状态和取消状态。
3. 从当前 next_sequence 分配 N 个连续序号，将 next_sequence 推进 N，并批量插入全部事件。
4. 全部提交成功后，通知回放服务读取本批次的最高已提交序号。

N 条事件从 2N 条写 SQL、N 个事务，变为 2 条写 SQL、1 个事务。逻辑事件行仍有 N 行；该优化主要减少往返、事务和运行行更新，不能把它描述成事件数据量也减少 N 倍。

### 不增加第二段等待

现有文本合并窗口是 50 毫秒或 1024 字符。批量提交要与这个窗口共用一次计时，不能串联成“文本合并等 50 毫秒，再等批次 50 毫秒”。

- 启动标记及时提交，不等待模型首段文字。
- 已达到原有文本发送时机的批次立即提交，不为了凑满数量继续等待。
- 工具调用/结果、审批、外部等待和控制事件到达时，将此前积累的事件连同边界事件一起提交。
- 源流结束、失败、取消或关闭时，进入明确的排空/终止流程，终态不能越过仍待提交的有效事件。
- 首期批次目标可设为 32 条、256 KiB，作为调参起点。单个合法事件超过这个目标时单独成批，仍遵循项目已有的大内容上限，不能因此截断工具结果或缩小既有能力。
- 保留有限队列和背压；不要用无界 buffer 或重叠事务提高吞吐。

SQL 放在 Mapper XML，通过 MyBatis-Plus/Mapper 执行；需要确认服务器收到的是多行 INSERT，而不是仅在 Java 中循环调用 insert。数据库事务不覆盖模型、Redis、文件或对象存储请求。

### 提交结果不确定时的处理

批次包含稳定的 appendId 和批内序号，建议在事件表增加相应字段及 `(run_id, append_id, append_ordinal)` 唯一约束。重试同一个批次必须复用身份，不能重新生成批次 ID。

如果连接在提交后断开，先查询整批是否已经提交，并核对内容摘要及序号；完整一致则返回已提交结果，完全不存在且所有者仍有效才重新追加。部分存在或内容冲突必须报数据完整性错误，不能使用 INSERT IGNORE 吞掉冲突。这个过程只重试数据库提交，不重新执行模型或业务工具。

## 4. 父运行引用子事件，正文只保存一次

不建议直接删除父事件，再按照 createdAt 拼接父子日志。并行子任务、同毫秒事件、迟到提交和多个实例都会让这种排序不稳定，而且当前前端只维护一个 `runId:sequence` 游标。

建议保持父运行的逻辑事件序列，增加明确的存储类型：

| 类型 | 保存内容 |
| --- | --- |
| INLINE | 事件正文、原始身份和本运行序号 |
| REFERENCE | 父运行序号、来源运行及来源序号、父工具调用和展示身份；不重复保存正文 |

例如，子事件 `(child-A, 17)` 保存一次工具结果。父事件 `(parent, 42)` 只引用它，并保存父页面展示所需的 parentToolCallId、agentName 等身份。对前端仍输出 `parent:42`，而不是把子运行游标混进父流。

### 父子必须在同一事务提交

当前先提交子事件，再复制到父运行，中间存在进程退出的窗口。改造时将子事件、父引用及两边序号放入同一事务：

1. 以统一顺序锁定父运行和子运行，校验两边所有者和租约。
2. 两边分别分配连续序号，各更新一次序号。
3. 在同一张事件表中，用一条多行 INSERT 写入子正文及父引用。
4. 提交后分别通知父、子回放服务。

对于 N 条需要展示在父运行中的子事件，当前为 4N 条写 SQL、2N 个事务；同批原子提交可以做到 3 条写 SQL、1 个事务：两次序号 UPDATE，加一次批量 INSERT。批次较大时按字节预算拆分，但每个子正文与对应父引用必须一起提交。

**仅把正文换成引用，不会自动减少写 SQL 次数。** 引用减少的是重复正文；减少次数依靠批量 INSERT、批量推进序号和父子事务合并。父引用仍然是一条持久化记录。

### 读取和边界条件

- 父回放先按父序号取一页引用，再批量查询来源正文；不能每条引用单独查询一次。
- SSE 的 runId、sequence、rawEventId、parentToolCallId 等沿用父记录身份，正文来自来源事件。禁止修改来源 JsonNode 后再供其他消费者使用。
- `AgentRunQueryService.collectToolDeltas` 和历史消息整理也必须通过统一的事件读取层取得正文。只修改 SSE 入口会导致重连后的工具参数或结果变空。
- 历史消息继续由来源运行生成一次，父引用不重复生成子历史。父工具返回的结果摘要仍保留。
- 引用创建时验证来源属于获准的父子执行关系；回放继续按父运行和会话授权，不能接受客户端任意指定来源。
- 来源缺失是完整性错误，不能跳过事件、返回空正文或推进游标。
- 使用直接指向原始正文的引用，避免形成多层引用链。多层子任务按既有观察范围生成引用，不扩大可见范围。
- `independentlyObserved` 的画布子任务保留独立观察方式，不强行写入父流。
- 父终态之后不再追加普通子事件引用。取消、失去所有者等情况下，子任务自身的终结和清理仍按现有状态机完成。
- 来源正文的保留期至少覆盖所有引用的可回放期。删除或归档按整个会话/执行树处理；不能只清理子正文、留下父引用。

## 5. 合并会话受理和历史消息保存

### 新会话受理

目前新会话先插入，再在受理任务时激活，保存首条用户消息时又更新计数。新会话可在一个受理事务中直接写入最终的 running 状态、message_count=1 和 next_message_order=2，并插入运行及用户消息。

本次短回复的受理部分由 5 条有效写入降为 3 条。已存在会话仍需锁行、核对归属和并发运行限制，然后将元数据、状态和消息计数合并为一次更新。不能通过客户端传入的会话 ID 覆盖其他用户会话。

模型配置、权限上下文和快照准备保持在短事务外；只有受理所需的状态校验和写入进入事务。

### 历史消息保存

一次消息整理事务先计算本批应生成的消息，按 projectionKey 校验既有记录，只为新增消息一次分配顺序范围，再批量插入，最后一次更新会话计数/时间/终态及一次更新运行的 projected_through_sequence。

- 普通文本收尾从 4 条写 SQL 降为 3 条。
- 本次只读工具的 3 条历史消息，收尾从 8 条降为 3 条。
- 本次业务 pipeline 的三个历史整理事务分别生成 3、21、8 条消息，现有 7、43、18 条写入合计 68 条；在每组能放进一条 INSERT 的条件下，可降为 9 条，节省 59 条。

消息、会话计数及整理进度保持同事务。事务失败时全部回滚，重启后从已提交的 projected_through_sequence 继续，不会重复消息、跳号或重复累计计数。大量消息仍按条数和字节分批，不把整个长任务一次性装入内存。

## 6. 心跳与通知

先保留 5 秒维护周期及当前租约时长。心跳返回失败还用于识别 CANCEL_REQUESTED；单纯延长间隔，会使 Redis 取消通知丢失时的响应变慢。

优先考虑同一实例在一次维护周期中批量续租：按统一锁顺序取得状态，一条批量 UPDATE 更新仍有效的运行，并分别处理失去所有者或已取消的运行。不能仅根据合计影响行数判断哪些运行成功续租。

进一步可在必要的事件序号更新中顺带续租，从而跳过本周期的独立续租写入，但必须保留每 5 秒的取消/所有者状态检查。只允许当前运行的执行者续租；子任务写父引用时不能据此证明父执行者仍存活。空闲等待模型期间仍需独立心跳。

Redis 已经每 25 毫秒合并唤醒通知，回放服务每 300 毫秒检查 MySQL。优化后仍只通知“某运行已提交到哪个序号”，不把 Redis 改成事件正文的唯一来源，也不因 Redis 超时阻塞数据库提交。

本次没有捕获到事件 outbox 的领取/完成 UPDATE，不能把删除这些更新计作当前收益。无关后台空更新单独评估，不混入本次对话优化的节省值。

## 7. 不改变的流式与恢复契约

| 故障或并发位置 | 必须保持的结果 |
| --- | --- |
| 批次未提交时进程退出 | 该批未对前端发布；已经展示的内容仍可从数据库回放 |
| 提交成功后、通知前退出 | 重连或 MySQL 周期读取找回全部事件 |
| 通知重复、乱序或全部丢失 | 只影响唤醒时机，正文与顺序仍由数据库决定 |
| 客户端在批次中间断开 | 按最后收到的单条事件序号恢复，批次剩余事件不丢失 |
| 两个子 agent 同时输出 | 父序号在父运行行锁下分配，回放顺序不会因重连改变 |
| 父子写入中途失败 | 子正文和父引用一起提交或一起回滚 |
| 取消与批次/终态竞争 | 按持久化状态和 ownerEpoch 决定唯一结果，旧执行者不能继续写 |
| 暂停等待审批或外部任务 | 先保存状态快照、候选/决定记录及等待状态，再发布可操作事件 |
| 状态快照保存失败 | 不发布成功终态，继续保留现有失败处理 |
| 事件已提交，历史消息尚未生成 | 从事件和整理进度补齐消息，不重新调用模型或业务工具 |

这里保持的是当前恢复能力：已提交内容可回放，等待和关闭恢复按已有流程处理，丢失所有者的普通执行按现有规则终结。不能把事件批量保存描述成可以从任意 token 自动继续供应商请求。

## 8. 按本次记录推算的收益

以下是固定本次模型输出、重试、心跳和业务操作后的 SQL 复算，不是改造后的压测结果。口径为包含收尾的有效写入，影响 0 行的语句另计。

| 样本 | 当前 | 精简生命周期＋合并受理/消息 | 再合并剩余父子事件提交 |
| --- | ---: | ---: | ---: |
| 智能助手短回复 | 36 | 21 | 21 |
| 智能助手长回复 | 42 | 27 | 27 |
| 智能助手一次只读工具 | 68 | 45 | 45 |
| 完整剧本解析 pipeline | 860 | 681 | 612 |

短回复：36 − 6×2 条生命周期写入 − 2 条新会话受理更新 − 1 条收尾更新 = 21。

完整解析：234 条事件中，59 条属于上述六类非发布生命周期记录，逐条写法对应 118 条 SQL；消息批量保存节省 59 条，新会话受理节省 2 条，得到 681。精简后还剩 69 条父引用，把每对父子事件的两次 INSERT 合成一次，再节省 69 条，得到 612。这里尚未计入多事件成批和心跳批量续租的收益。

不能把“删除原有全部 90 份父复制节省 180 条”“删除生命周期事件”和“批量提交”分别计算后直接相加，它们覆盖的记录存在重叠。引用本身也仍要保存。

短回复目标约减少 42% 的有效写 SQL；业务 pipeline 上述静态方案约减少 29%。字节数、redo/binlog、锁等待和首段延迟需要另行测量，不能只凭 SQL 数量推断数据库总压力同比下降。

## 9. 实施顺序与验收

1. 精简六类非发布生命周期记录，保留启动标记；合并会话受理与消息整理。先用短回复验证 36→约21 的目标，同时回归画布派发、外部等待恢复和关闭恢复。
2. 实现统一的有界批次写入、稳定提交身份和提交后通知。保持现有逻辑序号与 SSE 数据格式。
3. 加入 INLINE/REFERENCE 存储类型、批量读取正文和父子同事务写入，更新 SSE 工具详情及历史整理的读取路径。
4. 批量续租，必要时再评估事件提交顺带续租。取消检测时效不变。

迁移新增字段和约束，不修改已发布 V/B 脚本。实施时先核对远端正式版本，再确定新的迁移版本。现有记录明确标为 INLINE，保持原序号和游标；新 REFERENCE 正文缺失时直接报错，不回退复制或伪造空结果。

所有实例具备新格式读取能力后，才允许新运行写 REFERENCE。格式和持久化策略按运行固定，不能让同一运行在不同实例上临时改变规则。旧客户端仍使用同一 SSE 协议；历史 INLINE 记录与新记录都走明确的存储类型分支。

验收复用并补充 AgentJournalTerminalIT、AgentReplayLiveIT、AgentFencingCancellationIT、AgentWaitingStateIT、AgentProjectionRecoveryIT 和 AgentSlowJournalStreamingTests，重点覆盖：

- 批次中途失败、提交响应丢失后的重复提交、旧 ownerEpoch、取消和终态并发。
- 在批次内每个可见序号断开并重连，核对拼接正文、工具参数、工具结果和终态完全一致。
- 多个子任务交错输出、父子事务中断、来源缺失、跨会话引用、独立观察的画布任务及大工具结果。
- Redis 不可用、慢 MySQL、慢客户端和队列达到上限，确认执行期间仍持续输出，没有退化到结束后集中返回。
- 审批/外部等待和关闭恢复过程中强制退出，确认状态快照、待处理操作和模型请求身份保持正确，不重复执行业务副作用。
- 原有历史数据重连、消息计数与顺序、关闭后再次读取、会话删除及正文保留期。

最后在相同模型及固定输入下重跑七组测试，同时使用可控分块的模型响应做延迟对照。记录首段和段间延迟、事务耗时、写 SQL、写事务、正文存储字节、锁等待及队列峰值。只有正文、顺序、控制状态和故障恢复均通过后，才把静态推算改为实测结论。
