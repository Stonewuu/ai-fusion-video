# Redis 流式回放与完整消息持久化方案

状态：已实现并完成验证，最终范围和结果见 [交付总结](../3-completed/20261124-Redis流式与消息持久化/completion-summary.md)。本文保留设计讨论记录。

本次保证应用正常运行时消息和工具结果不丢失，支持浏览器断网重连。MySQL 按完整消息、工具调用和控制状态保存，Redis 保存流式片段用于实时读取和重读。不新增消息入库后的 Redis 主动删除、裁剪或过期流程，不扩展异常退出后的数据恢复机制，不修改 Redis 持久化配置。

## 保存范围

| 数据 | 保存位置与时机 |
| --- | --- |
| 文本、思考和工具执行中的增量片段 | Redis Stream，写入成功后对外发送，不逐片写 MySQL |
| 完整助手消息或工具前已经完成的一段回复 | MySQL，一条逻辑消息保存一次正文 |
| 工具调用标识、完整参数及执行身份 | MySQL，在允许执行工具后、实际执行前保存 |
| 工具结果或失败结果 | MySQL，在结果产生后保存，再交给框架继续执行 |
| 审批候选、用户决定、外部等待、取消和运行终态 | MySQL，在状态变化时保存 |
| 执行上下文、模型请求身份、业务幂等记录 | 沿用必要的现有保存 |
| 内部生命周期诊断 | 按需要记录日志，不将全部 SDK 事件写入 MySQL |

afv_agent_event 不再承担文本增量日志，低频控制记录按现有状态管理需要保留。afv_agent_run 不再因为每个文本片段更新 next_sequence。MySQL 保留消息顺序、运行状态及必要控制版本，Redis 管理流式读取位置。

一条工具调用仍有开始和结束两个保存时机：开始时保存参数和身份，完成时保存结果。保存为一条调用记录时，可以先 INSERT、完成后 UPDATE。

## 正常执行流程

完整消息不是整个 agent 任务。一次任务可能先输出说明，再调用工具，最后回复；每个已经完成的文本段和工具结果及时写入 MySQL。

1. 用户消息进入 MySQL。
2. 模型输出的片段进入 Redis Stream，前端持续显示。
3. 助手消息完成后，将完整正文写入 MySQL，并更新会话信息。
4. 工具按调用开始和结果产生两个边界保存完整记录。
5. 当前应保存的消息、工具结果和 AgentState 保存成功后，提交运行终态，再发布完成通知。

消息保存链路属于执行完成条件，不能作为未等待完成的后台操作丢弃。写入异常按现有错误处理返回，不吞掉异常后宣告保存成功。

用户主动停止或模型返回失败时，应用仍在运行，保存已经收到的文本及对应状态。模型重试按照 replyId/attemptId 隔离不同尝试，不把失败尝试的半段文本拼到新的回复中。

消息写入成功后，Redis 中的流式数据继续保留供重读，不追加主动清除步骤。本次不增加归档回收任务、独立归档确认流程或新的缓存保留期策略。

## Redis 组织与回放

使用 Redis Stream 保存有顺序的增量，浏览器按自己的流游标继续读取。Pub/Sub 可以用于通知，但不承担片段重读。

每个需要整体观察的根运行使用一条流，片段包含 sourceRunId、messageId、replyId、blockId、toolCallId 和 parentToolCallId。子 agent 以来源身份进入父时间线，不再向 MySQL 复制一份父事件正文。独立观察的画布子任务继续使用自己的流。

消息 ID 在开始时确定并保持不变。应用在执行过程中按消息和内容块累积完整正文，结束时保存；Redis 中的片段用于实时读取和重连，不再额外维护一套为进程退出接管设计的待归档状态。

MySQL 中的消息版本与 Redis 流位置分开：

- Redis 游标用于接续流式片段。
- MySQL 消息 ID、顺序和版本用于已完成历史。
- 前端按 messageId 处理草稿和完整消息；完整消息到达时替换草稿，重复通知不重复追加正文。
- 页面重新打开时加载已保存的历史消息，再接续当前运行中的流式内容。已经完成的消息不因重读旧片段而再次追加。

当前前后端使用 runId:sequence，并将其与 MySQL 事件序号绑定。需要同步调整控制器、流读取、状态接口和前端游标处理，让流式序号不再依赖数据库逐片更新。

正常运行期间完整保留用于重读的片段，不沿用旧方法每次写入后裁剪至 200 条的行为，也不直接套用旧方法的一小时过期设置。本次不新增主动清理机制。

## 消息与工具的保存一致性

按稳定消息 ID、工具调用 ID 保存数据，避免重连或重复通知造成重复记录。消息正文、消息计数和顺序在同一批数据库事务中更新，不在每个流式片段后重复更新会话。

并行子任务各自按消息 ID 保存正文，通过来源运行及父工具调用关联到同一会话。一个子任务完成不代表其他子任务也完成，运行终态需要等待本次应保存的结果处理完毕。

工具参数、工具结果与调用身份保持关联。沿用现有权限校验、requestId/toolCallId 和业务命令回执，不通过重新执行工具处理消息重复投递。

AgentState 沿用框架在执行结束、暂停及可处理失败时的保存。权限未变化时减少重复状态保存的优化可以单独实施，不与本次流式存储调整混合。

## 代码调整范围

- DefaultRunExecutionSupervisor：增量进入 Redis，完整消息和工具边界触发 MySQL 保存，等待应保存结果完成后提交终态。
- AgentRunReplayService：改为 Redis 增量重读；已完成历史由 MySQL 消息接口提供。
- AgentMessageProjectionService：接收执行过程中累积的完整消息，不再依赖数据库逐片事件拼接正文。
- AgentRunQueryService：工具参数和结果读取完整的调用记录，停止依赖 MySQL selectToolDeltas。
- PlatformSubAgentRunService.awaitCompletion：从已保存的子运行终态和完整输出取得结果，Redis 用于过程展示和通知。
- AgentScopeToolAdapter：衔接工具开始、结果保存与框架继续执行，保留现有权限和业务幂等校验。
- 画布派发：现有代码通过 next_sequence 判断执行是否开始，改为明确的执行启动标记，保留现有派发判断。
- 前端：区分流游标与消息版本，按 messageId 更新草稿和完整消息，处理重连后的重复片段及不同模型尝试。

AiStreamRedisService 已有旧 Stream/List 方法，但其 Stream 上限为 200 条、保留时间为一小时，publish 捕获异常后返回 null。新主链需要使用符合本方案的写入和读取方法，不能直接套用旧方法。其他模块继续使用的旧方法不在本次范围内。

旧版 MySQL 事件回放和新版 Redis 游标通过明确协议版本区分，保留已有历史读取能力；新运行只写新路径，不逐片双写 Redis 与 MySQL。涉及表结构时遵循新版本 Flyway 迁移规则。

## 收益与验收

一条回复即使分成 200 个片段，也只形成一条完整消息正文，不再因此产生 200 条 MySQL 增量事件和 200 次运行序号更新。会话信息、工具开始/结束、运行状态和 AgentState 的必要写入仍然存在。

此前 36→21、860→612 的数字属于保留 MySQL 事件日志的备选方案，不沿用为本方案的预估结果。实施后重新统计完整执行中的 MySQL 写入次数和流式延迟。

验收覆盖：

- 短回复、长回复及含多段文本的工具调用，最终消息内容完整。
- 流式输出过程中浏览器断开、刷新和重连，正文不遗漏、不重复拼接。
- 超过旧 200 条限制的回复、长时间执行及多个子 agent 交错输出。
- 工具调用参数、成功和失败结果、审批及用户主动取消的记录完整。
- 同一消息重复处理不重复插入，消息顺序和计数正确。
- 完成状态发出前，完整消息、工具结果及必要上下文已保存成功。
- 消息保存后没有新增 Redis 主动删除或裁剪操作。
- 旧消息和旧运行保持可读取。

本次按正常运行的数据完整性及流式重读要求实施和验收，不增加异常退出、Redis 数据丢失后的额外恢复目标。
