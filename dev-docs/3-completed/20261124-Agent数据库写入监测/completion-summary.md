# Agent 数据库写入实测结果

2026-11-24，基于工作区提交 `5b8e6cc` 的后端构建完成七组测试。智能助手与 pipeline 共用执行引擎，但一条消息的写库次数取决于事件数、运行时间、模型调用、子 agent 和业务操作，不是固定次数。

## 环境与统计口径

使用本地独立测试服务、临时 MySQL 8.0 容器及 Redis 的 15 号数据库。临时 MySQL 复制本项目的表结构、Flyway 历史、模型和必要初始化配置；测试用户、会话和剧本资料单独创建。模型请求使用已配置的 Vertex AI 协议、`gemini-3.8-flash` 模型，没有使用模拟模型。

通过前端使用的 `/api/ai/pipeline/run` 接口发消息。六组对照均为新会话，使用相同默认智能体和模型，分别设置 `assistant`、`pipeline` 分类。业务测试使用剧本解析界面的 `script_full_parse` 智能体、`FULL_ACCESS` 工具模式和一个短分集。

MySQL Performance Schema 持续记录 SQL、影响行数、线程与事务身份，并与最终事件及消息记录交叉核对。

- **结束前**：从提交请求开始，到根运行写入 `COMPLETED` 的事务提交，包含这次终态提交。
- **写 SQL**：本条请求及其子运行、业务操作执行的 INSERT、UPDATE、DELETE。一条语句记一次，影响 0 行的请求内语句也计入。
- **有效写入**：上述语句中 MySQL 报告影响行数大于 0 的语句数量。状态快照使用 INSERT … ON DUPLICATE KEY UPDATE，即使影响行数为 2，也只计一次。
- **写事务**：包含有效写入且已提交的事务，不包含只有查询或空更新的事务。
- 与请求无关的后台定时轮询、过期检查和清理单独排除。子运行及业务事务中影响 0 行的语句通过事务身份归入请求。
- 继续采集结束后的消息保存。这里的次数是 SQL/事务数量，不是磁盘刷写次数。

## 实测次数

| 场景 | 入口 | 耗时（秒） | 结束前写 SQL | 其中 UPDATE | 结束前有效写入 | 结束前写事务 | 结束后追加写入 | 完整保存有效写入 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 只回复“监测完成。” | 智能助手 | 16.45 | 33 | 17 | 32 | 18 | 4 | 36 |
| 相同短回复 | pipeline 对照 | 19.36 | 34 | 18 | 33 | 19 | 4 | 37 |
| 请求约 1200 字短文 | 智能助手 | 23.78 | 39 | 21 | 38 | 22 | 4 | 42 |
| 相同长文请求 | pipeline 对照 | 30.25 | 40 | 22 | 39 | 23 | 4 | 43 |
| 查询一次项目列表 | 智能助手 | 54.02 | 61 | 35 | 60 | 36 | 8 | 68 |
| 相同只读工具请求 | pipeline 对照 | 82.53 | 67 | 41 | 66 | 42 | 8 | 74 |
| 一个短分集的完整剧本解析 | 业务 pipeline | 490.57 | 850 | 492 | 842 | 457 | 18 | 860 |

六组对照各有一条结束清理 UPDATE 影响 0 行。业务 pipeline 有两条这样的 UPDATE，以及六条没有匹配记录的媒体绑定 DELETE；其结束前的 850 条写 SQL 为 352 条 INSERT、492 条 UPDATE、6 条 DELETE。

普通短回复和长回复结束后增加的 4 条写入，分别是：新增助手消息一次、更新会话两次、更新运行的历史消息保存进度一次。只读工具场景还需保存工具调用和工具结果，因此追加 8 条。业务 pipeline 在根运行结束前已经保存子运行的历史，根运行结束后再追加 18 条。

## 两种入口为什么会相差几次

| 场景 | 智能助手事件数 | pipeline 事件数 | 智能助手心跳 | pipeline 心跳 | 扣除心跳后的结束前有效写入 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 短回复 | 9 | 9 | 3 | 4 | 两者均为 29 |
| 长回复 | 11 | 11 | 5 | 6 | 两者均为 33 |
| 一次只读工具 | 17 | 17 | 11 | 17 | 两者均为 49 |

这些对照组中，两种分类的事件数量、模型调用次数和消息保存方式一致，差异全部来自心跳。维护任务默认每 5 秒运行一次；模型返回较慢时，会多更新运行记录的心跳和租约。长文的实际输出分别为 1750 和 1685 个字符，均形成 3 条文本增量事件。

六组对照全部通过以下同一链路：

`AiPipelineController → AgentScopePipelineRunService → DefaultRunExecutionSupervisor → AgentExecution/HarnessAgent`

前端智能助手的连接协调器与 pipeline store 都调用 `pipelineStream()`。会话分类主要影响会话组织；业务 pipeline 指定的智能体、工具与子 agent 配置会改变执行内容。

## 写入发生在哪里

以智能助手短回复的完整保存过程为例：

| 表 | 有效写入次数 | 用途 |
| --- | ---: | --- |
| `afv_agent_run` | 14 | 创建运行、推进事件序号、3 次心跳、终态和历史保存进度 |
| `afv_agent_event` | 9 | 保存运行、模型和文本事件 |
| `afv_agent_conversation` | 5 | 创建会话、分配消息顺序、更新消息数量和状态 |
| `afv_agent_message` | 2 | 保存用户消息和最终助手消息 |
| `afv_agent_state` | 2 | 开始时项目设置工具权限触发保存，结束时框架保存执行上下文 |
| `afv_agent_model_call_usage` | 2 | 创建模型调用记录并保存完成用量 |
| `afv_agent_model_request` | 2 | 创建模型请求记录并保存完成状态 |
| 合计 | 36 | 32 条发生于根运行终态提交前，4 条发生于其后 |

流式输出经过合并后，每条事件会在一个事务中执行两条写 SQL：更新 `afv_agent_run.next_sequence`，再插入 `afv_agent_event`。默认合并条件为 50 毫秒或 1024 字符，事件类型和身份变化也会触发提交。消息表不随每条文本增量反复更新；结束时从事件记录整理历史消息。

当前六组对照中，每个运行保存两次状态快照。进一步核对当前 AgentScope 2.0.4 源码确认：开始时的保存由项目 `applyRequestedPolicy()` 调用 SDK `setPermissionMode()` 触发；结束时由框架 `ReActAgent` 保存执行上下文。两次都通过项目配置的 MySQL AgentStateStore 写入。用量记录已经写入，结算标记仍为 `PENDING`；本次采集没有观察到额外结算写入。

## 业务 pipeline 的额外写入

完整解析使用一个主 agent 和一个 `episode_scene_writer` 子 agent，最终两个运行均为 `COMPLETED`，保存了一个场次和三个素材。执行中共记录 17 次模型调用尝试，13 次完成、4 次失败后自动重试，重试造成的写入包含在结果中。

父运行保存 143 条事件，其中 90 条复制自子运行；子运行保存 91 条事件，总计 234 条。父子运行共执行 160 次心跳。完整保存的 860 条有效写入可以分解为：

| 类型 | 有效写入次数 |
| --- | ---: |
| 234 条事件及对应运行序号更新 | 468 |
| 父子运行心跳 | 160 |
| 运行创建及历史保存进度 | 5 |
| 会话记录 | 37 |
| 历史消息 | 34 |
| 状态快照 | 8 |
| 模型调用用量及模型请求记录 | 68 |
| 素材、场次、剧本及业务变更记录 | 80 |
| 合计 | 860 |

其中，90 条子事件复制到父运行又产生了 180 条写 SQL。子 agent 的一条普通事件在自身运行和父运行分别保存时，会产生四条写 SQL、两个事务。这个行为与普通对话共用执行引擎，但数据保存范围已经不同。
