# Redis 流式与完整消息持久化优化

已在 `feat/agent-redis-stream` 分支完成实现和验证，前后端开发版本为 `1.4.2`。改动保存在工作区，尚未提交或发布。

## 最终行为

- 智能助手和 pipeline 共用新执行链路。文本和思考片段写 Redis Stream，流式序号也由 Redis 分配，不再逐片新增 MySQL 事件或更新运行序号。
- 一条助手回复在模型调用结束时保存完整正文与思考。准备执行的工具参数在执行前保存，工具结果在下一轮推理前保存；同一轮回复和工具参数合并 INSERT，更新一次会话计数。
- 工具参数和工具结果继续各保存一条消息，沿用历史消息展示约定。审批拒绝只保留审批记录产生的结果，跳过 SDK 的重复拒绝回显。
- 子 agent 将带有来源标识的事件直接写入父运行的 Redis 展示流，数据库只保存子运行自己的完整消息和控制记录。独立展示的画布节点子运行使用自己的展示流。
- 断线后按原游标重读 Redis。完整消息按回复标识替换草稿，重复接收不会重复拼接；审批结果先于恢复后的工具结果发送。用户取消时保存已经接收并展示的部分回复，再提交终态。
- MySQL 保留启动、审批、等待、取消、终态以及框架执行上下文、模型请求和业务写入。普通无审批运行的事件表只留下启动和结束两条记录。
- 本次没有新增 Redis 删除、裁剪、TTL 或持久化配置。历史运行依据协议版本继续读取 MySQL 事件。

## 写入实测

使用隔离 MySQL 和应用实例，调用与此前监测相同的 Vertex `gemini-3.8-flash`。统计有影响行且已提交的写 SQL，排除后台无影响行的定时 SQL；“全程”包含终态提交后的消息整理与事件发布。

| 场景 | 终态提交前，优化前→后 | 全程，优化前→后 | MySQL 事件数，优化前→后 |
| --- | ---: | ---: | ---: |
| 智能助手短回复 | 32→20 | 36→23 | 9→2 |
| 智能助手长回复 | 38→22 | 42→25 | 11→2 |
| 智能助手项目查询工具 | 60→28 | 68→31 | 17→2 |
| pipeline 短回复 | 33→26 | 37→29 | 9→2 |
| pipeline 单集剧本解析，父+子运行 | 842→236 | 860→239 | 234→4 |

短回复全程减少约 36%，长回复约 40%。总写入还受到模型耗时、调用次数和业务操作影响：pipeline 短回复此次耗时更长，心跳从 4 次变为 9 次；剧本解析模型调用从 17 次变为 13 次，心跳从 160 次变为 29 次。因此，不能把两次复杂任务总 SQL 的全部差异都归因于本次改造。

逐项核对了返回的完整消息、工具参数和工具结果与 MySQL 内容。剧本解析保存 2 条助手消息、28 条工具消息，父子运行合计只有 4 条数据库控制事件，没有复制子运行的逐片事件。一次没有正文的模型返回未纳入长回复对比，详见技术债务记录。

## 验证结果

- 后端完整单元测试执行 1208 项，1207 通过、1 项已有跳过；随后补充拒绝回显和租约校验用例，相关单元测试和流式集成测试复测通过。正常执行保存消息时校验租约，取消确认结束租约后仅允许原执行者保存已展示内容。最终后端打包成功。
- 31 项相关集成测试通过：旧事件重放 4 项、历史消息整理 10 项、等待状态 9 项、子运行管理 6 项、新流验收 2 项。新流验收覆盖 240 段模型输出、首段展示、断线与刷新重读、父子委派、批准/拒绝、取消、已读终态重连，以及 4 个并发写入者的 400 条事件分页重读和去重。最后一次首段延迟 205ms，后续事件延迟 P95 为 115ms。
- 前端 43 项回归测试通过，覆盖两处时间线的完整消息替换、子运行审批身份、协议版本、重连去重和模型重试；TypeScript 检查与生产构建通过。
- 新增 `V1.1.4.2.0__agent_stream_protocol.sql`，Flyway 命名校验通过；新建数据库与复制现有结构的测试数据库均完成校验和迁移。

验证通过 HTTP 接口、流式客户端和自动化测试完成。未进行 Chrome 页面验收。用户原有 `comments-panel.tsx` 修改保持原样。
