# 1.3.0 迁移合并与发布准备

## 修改范围

1.3.0 尚未正式发布，本次把 38 个开发迁移合并为 7 个，按照画布文档、业务命令、托管媒体、生成任务、画布执行、智能体配置和媒体视图分组。61 张新表直接包含最终字段、索引和约束，ALTER TABLE 从 32 条减少到 15 条，每个已有表的相关修改放在同一条语句里。视图按照依赖顺序只创建最终定义，SQL 语句总数从 111 条减少到 84 条。

已经发布的 27 个 SQL 文件保持原样。已有图片、视频任务的个人归属回填，以及变更通知和调度锁的初始化数据继续保留。删除的五条回填只处理本版本中新建的表，从正式版本升级时这些表还没有业务数据，所以不再执行这些开发过程中的过渡操作。

涉及中间开发迁移的测试已经改成从正式 1.2.0 升级，或者直接验证最终约束。测试仍检查历史数据保留、已有个人归属不被覆盖、团队任务不被误归属、生成请求幂等、模板来源约束和已有提供商配置保留。

完整回归还发现模型配置为空时，OpenAI 参考图上传直接读取配置会出现空指针。现在通过现有配置读取方法获取可选字段，未设置时仍使用 OpenAI 的 image[] 字段。画布时长测试分别覆盖默认时长、自动时长和指定时长；前端测试脚本的模块变量命名也已通过 lint。

## 本地数据库

本地 ai_fusion_video 已完整备份，并先在隔离 MySQL 中还原、验证同步过程。确认实际结构一致后，重新创建四个最终视图，再把原来的 38 条开发迁移记录同步为新的 7 条记录。99 张业务表的数据校验值保持一致，26 条已发布版本的迁移记录原样保留，Flyway validate 已通过。

本地后端已经恢复启动，启动时再次成功校验 34 个迁移文件，并确认数据库无需再次迁移。前端继续使用 3000 端口，后端使用 18080 端口。

AgentScope 2.0.4 启动时自行维护的 afv_agent_state.version 字段保留原状。旧开发迁移反复替换上游视图后，下游视图会保留旧的字段元数据，因此本次按照依赖顺序重建视图，使其与新安装一致。本次没有修改其他项目数据库。

## 验证结果

- MySQL 8.0：原迁移、合并迁移以及基线首次安装的表、字段、索引、约束和最终视图逐项一致；正式版本的样例数据升级结果一致。
- MySQL 8.4：迁移与相关业务回归 93 项通过，包含命名、首次安装、正式版本升级、媒体保留、业务命令和请求协议检查。
- 后端：完整测试 907 项通过，开启真实 FFmpeg 测试，没有失败或跳过。
- 前端：181 项脚本测试及生产构建通过，lint 没有错误，仍有 6 条现有警告。
- 提交检查：已排除本地数据库备份、验收附件和本地配置，git diff --check 通过。

## 使用范围

从已发布版本升级时，由 Flyway 正常执行新迁移即可。已经运行过旧 1.3.0 开发迁移的其他数据库，仍须先备份并核对实际结构，再同步迁移历史；不能直接重跑合并后的建表脚本，也不能只运行 repair。

版本分支沿用已有的 v- 命名方式，本地和远端均为 v-1.3.0。按用户要求，版本准备改动合并为一个提交，后续画布验收修复和文档归档也并入这个提交。代码推送到 origin/v-1.3.0 后核对远端一致，用于后续版本发布准备。前后端 HTTP 检查均返回 200，隔离验证容器已清理，本地数据库备份继续保留。
